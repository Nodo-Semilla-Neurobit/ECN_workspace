## 3.3. WRIL: La Capa de Resolución, Integridad y Circulación del Workspace

### 3.3.1. El Principio Fundamental: DECLARACIÓN ≠ REALIDAD

La Instancia 3 de la arquitectura táctica de la ECN corresponde a la **Corteza Cerebral**: el monitoreo forense y la autocuración. Esta instancia se materializa en la **Capa de Resolución, Integridad y Circulación del Workspace (WRIL)**.

WRIL es la capa que se encuentra entre el "código funcional" de la ECN y el estado físico del workspace. Su responsabilidad es conseguir que los módulos puedan encontrarse, reconocerse, trasladarse, repararse, verificarse y relacionarse físicamente sin depender de rutas rígidas ni perder su historia.

El principio fundamental que WRIL materializa es:

```
DECLARACIÓN ≠ REALIDAD
```

Un archivo puede declarar una ubicación en su encabezado MFN, pero residir físicamente en otra. Un script puede apuntar a una ruta antigua que ya no existe. Una dependencia puede estar instalada en un path que el módulo no conoce. WRIL es la capa que detecta, reconcilia y registra estas discrepancias. No como una frase filosófica, sino como un fenómeno que provoca una operación concreta.

### 3.3.2. El Ciclo de Coherencia Física

WRIL no es un módulo monolítico. Es una tríada de componentes que operan en secuencia, ejecutando un ciclo de cinco fases:

```
DISCOVER → RESOLVE → RECONCILE → VERIFY → RECORD
```

| Fase          | Operación                                           | Componente Principal |
|---------------|-----------------------------------------------------|----------------------|
| **DISCOVER**  | Descubrir el estado real del filesystem             | WS-Sentinel          |
|---------------|-----------------------------------------------------|----------------------|
| **RESOLVE**   | Localizar recursos mediante direccionamiento lógico | PathResolver         |
|---------------|-----------------------------------------------------|----------------------|
| **RECONCILE** | Corregir referencias obsoletas y alinear declaración| PatchResolver        |
|               | con territorio                                      |                      |
|---------------|-----------------------------------------------------|----------------------|
| **VERIFY**    | Comprobar coherencia de dependencias e integridad   | Dependency Scanner   |
|               |                                                     | / Testers            |
|---------------|-----------------------------------------------------|----------------------|
| **RECORD**    | Registrar la identidad declarada y la trazabilidad  | MFN File Registry    |
|               | histórica                                           |                      |
----------------------------------------------------------------------------------------------

### 3.3.3. Los Componentes de la Tríada

**1. WS-Sentinel (El Guardián de la Frontera)**

Componente reactivo que vigila `inbox/` mediante `inotifywait`, detecta eventos CREATE, identifica archivos compatibles y extrae su `MFN_LOCATION`. Después los dirige a su ubicación declarada.

```
EXTERIOR/ GENERACIÓN
    ↓
inbox/
    ↓ CREATE event
WS-SENTINEL
    ↓ lee MFN_LOCATION
    ↓ valida destino
destino OK → MOVE → registro histórico
destino ausente → backup → crear/ pedir
```

Cuatro propiedades importantes:
1. **Operación local**: no depende de servicios externos.
2. **Automatización mediante inotify**: reacciona a eventos del filesystem.
3. **Backups antes de sobrescribir**: preserva el estado anterior.
4. **Trazabilidad mediante el mapa de ubicación**: registra cada movimiento.

WS-Sentinel decide dónde pertenece físicamente un archivo según la declaración que el archivo trae consigo. No decide qué significa un archivo.

**2. Path Map (El Estado Indexado del Workspace)**

El workspace posee un estado físico, pero los módulos no recorren el disco cada vez que necesitan encontrar otro módulo. Existe `path_map.json`, un índice centralizado que permite desacoplar los módulos de las rutas absolutas.

```
DISCO
    ↓ scan
PATH MAP
    ↓ lookup
MÓDULO
```

La regeneración de `path_map.json` es la lista de ubicación de los artefactos en la topología del workspace. Es un índice. **No es el workspace**. Esta distinción es crítica: el mapa puede estar desactualizado respecto del territorio.

**3. PathResolver (Direccionamiento Lógico)**

Proporciona la locación dinámica de los archivos en la ECN, consultando el mapa. Su operación esencial es `resolve(filename)`. Carga `path_map.json`, busca el identificador y devuelve la ruta correspondiente. Si no encuentra el archivo, regenera el mapa y vuelve a intentar.

La diferencia entre los tres componentes:

| Componente          | Función                   | Pregunta que responde |
|---------------------|---------------------------|-----------------------|
| `generate_path_map` | construye el índice       | —                     |
| `PathResolver`      | consulta el índice        | ¿Dónde está?          |
| `WS-Sentinel`       | modifica el estado físico | ¿Dónde pertenece?     |

### 3.3.4. Reparación y Registro

**PatchResolver (Reparación de Referencias)**

El problema que resuelve es:
```
EL ARCHIVO EXISTE + EL SCRIPT EXISTE + PERO EL SCRIPT APUNTA A UNA RUTA ANTIGUA
```

`sos_path_fixer.py` (primera implementación de PatchResolver) carga `path_map.json`, reconoce patrones de rutas hardcodeadas, crea un backup antes de modificar y busca coincidencias en el mapa.

El flujo completo de `PatchResolver`:
```
locate_target()
    ↓
detect_stale_reference()
    ↓
resolve_target()
    ↓
generate_patch()
    ↓
backup()
    ↓
apply()
    ↓
verify()
```

PatchResolver se constituye como el puente entre memoria lógica y realidad física encargado de: detectar → validar → modificar → verificar → registrar.

**MFN File Registry (Identidad Declarativa)**

Mientras `path_map` responde "¿Dónde está?", el registry responde "¿Qué declara ser este archivo dentro de la estructura MFN?".

La implementación busca:
```
MFN_LOCATION
MFN_LEVEL
MFN_COORD
```

y construye un índice de metadatos. Aunque parece similar al sistema anterior, **no deben fusionarse pues tienen tareas diferentes**:

```
PATH MAP      = estado físico
MFN REGISTRY  = identidad declarada
```

Esa separación permite detectar eventualmente:
```
DECLARACIÓN ≠ REALIDAD
```

Ejemplo:
```
Archivo declara: MFN_LOCATION: core/
Filesystem:      ~/ECN/modules/foo.py
```

Eso es una inconsistencia detectable. Y ahí empieza a aparecer una verdadera capa de integridad.

**Oportunidad para patch_resolver:**
Como motor de reconciliación entre referencias lógicas y estado físico, detecta:
```
REFERENCIA DECLARADA
    ↓
RESOLUCIÓN
    ↓
ESTADO ACTUAL
    ↓
COHERENTE → NO-OP
NO        → PATCH
            ↓
            BACKUP
            ↓
            APPLY
            ↓
            VERIFY
            ↓
            COMMIT
```

**EVITAR QUE LA CAPA SE CONVIERTA EN "supermódulo"**

La arquitectura debe conservar estas fronteras:

| Componente         | Responsabilidad                |
|--------------------|--------------------------------|
| WS-SENTINEL        | observa y enruta               |
| PATH MAP           | indexa                         |
| PATH RESOLVER      | localiza                       |
| MFN REGISTRY       | interpreta identidad declarada |
| PATCH RESOLVER     | reconcilia referencias         |
| DEPENDENCY SCANNER | determina requisitos           |
| TESTERS            | verifican comportamiento       |
| BATCH EXECUTOR     | ejecuta operaciones            |

Cada módulo tiene una pregunta diferente, lo que permite que la capa sea modular.

## 3.4. El Arca y el Registro Inmutable (Instancia 4)

### 3.4.1. La Instancia 4: El Núcleo Inmutable

La cuarta y última instancia de la arquitectura táctica es **El Arca (Núcleo)**. Su mecanismo de control es el Registro MFN, la Matriz Fractal y el formato JSON-L. Su función en la resistencia es proveer una **estructura no conmutativa** que mapea el estado del concepto (como hexagramas del I Ching) de forma inmutable.

El Arca es el destino final de toda operación validada. Cuando el Verbo ha atravesado la emisión, el transporte, la validación sintáctica (Neurobit Protocol v1.1) y la reconciliación física (WRIL), su resultado se asienta en el Arca.

### 3.4.2. memoria_eva.jsonl y el Ledger Soberano

El protocolo Neurobit v1.1 establece que, en su Fase 5 (Registro), cuando el entorno disponga de un mecanismo persistente, la operación debe documentarse en:

```
memoria_eva.jsonl
```

El registro debe preservar, como mínimo:
```
timestamp / ACTION_WORD / CLASS / estado_de_validación / identificador_del_contenedor / resultado
```

Este archivo JSON-L (JSON Lines) constituye el **Ledger Soberano** de la ECN. Es un registro inmutable, local y append-only que garantiza la trazabilidad histórica de cada intención materializada. La persistencia efectiva depende del sistema que implemente la ECN; el protocolo por sí solo no crea almacenamiento inmutable, pero exige su existencia para que el Logos Genuino pueda ser auditado.

### 3.4.3. El Panóptico Invertido: Auditoría Forense Ciudadana

- **Matriz Hermitiana (Simétrica)**: Captura el contenido Lógico, el núcleo puro y crudo de la acción sin adornos.
- **Matriz Antihermitiana (Asimétrica)**: Captura el contexto implícito, la emoción, el sesgo y la dinámica de poder del emisor.

Al aislar matemáticamente estas mitades a nivel local (IP 127.0.0.1), el sistema ejecuta un Panóptico Invertido.

> *"En el juego, no son las corporaciones las que nos vigilan a través de la red; es el Homo Vivo, desde su jaula de Faraday semántica, quien utiliza su IA local y sus archivos JSON-L inmutables para auditar y desmascarar las mentiras y alteraciones de las bases de datos públicas de las instituciones del viejo mundo."*

Es una herramienta cívica de auditoría forense ciudadana. Es la **LOGIA TRANSPARENTE DE LA VERDAD**, una antítesis al funcionamiento hermético de las logias que actualmente operan en la sombra. El Panóptico Invertido no vigila para controlar; vigila para **verificar la coherencia entre lo declarado y lo manifestado**.
