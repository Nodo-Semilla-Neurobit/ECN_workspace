## 4.1. El Camino del Aspirante (Re-alfabetización Tecnológica)

### 4.1.1. El principio fundamental

La gamificación del Camino del Aspirante es una **interfaz pedagógica del propio proceso de ensamblaje**. El aspirante obtiene un reconocimiento porque acaba de adquirir una capacidad real.

La secuencia de adquisición es:

```
entender filesystem → usar terminal → leer estado → crear entorno aislado →
resolver dependencia → comprender proceso → identificar módulo → interpretar contrato →
ejecutar dry-run → verificar → integrar
```

La recompensa es una representación simbólica de una competencia técnica efectivamente adquirida. Eso hace que el juego sea compatible con el principio SINCERO: se declara la Presencia de una capacidad verificable.

> *"La ECN no debería enseñar dependencia de la ECN. El sistema tiene que producir usuarios progresivamente más capaces de comprenderlo, inspeccionarlo, modificarlo y eventualmente cuestionarlo."*
> — F5, diálogo CBC-LLE, §15

### 4.1.2. El error se debe interpretar como Tensión y no significa un 'fracaso'

La idea de "Absorción de Tensión" merece conservarse, pero con una distinción técnica fundamental:

```
ERROR ≠ FRACASO DEL ASPIRANTE
```

Un error de comando puede significar:

- sintaxis incorrecta
- ruta inexistente
- dependencia ausente
- permiso insuficiente
- servicio detenido
- contrato inconsistente

Cada uno representa una **oportunidad de diagnóstico**. El ciclo pedagógico del error es:

```
INTENTO → RESULTADO → TENSIÓN → DIAGNÓSTICO → CORRECCIÓN → NUEVO INTENTO → VERIFICACIÓN
```

El sistema debe decir algo equivalente a:

> *"La estación detectó una tensión. El siguiente conocimiento necesario es..."*

Esto tiene una consecuencia pedagógica fundamental: el usuario aprende a leer errores como información del sistema. Y eso es exactamente lo que necesita alguien que va a operar una estación Linux real.

### 4.1.3. La progresión: de Usuario a Nodo Semilla

No se trata solamente de aprender comandos. Se trata de pasar de:

```
USUARIO DE INTERFAZ → LECTOR DEL SISTEMA → OPERADOR DEL SISTEMA
```

La progresión completa:

| Etapa | Rol              | Operación            |
|-------|------------------|----------------------|
| 1     | **USUARIO**      | consume interfaces   |
| 2     | **EXPLORADOR**   | observa el sistema   |
| 3     | **OPERADOR**     | ejecuta y verifica   |
| 4     | **ARQUITECTO**   | comprende relaciones |
| 5     | **NODO SEMILLA** | co-crea              |

Eso es más sólido que presentar la ECN como simplemente "un software futurista". Es una **travesía de descubrimiento** donde cada concepto narrativo corresponde a una capacidad técnica real.

### 4.1.4. Tres tipos de progreso (más uno)

No se utiliza una única barra. Se mantienen tres estados independientes:

**CONOCIMIENTO** — Representa lo que el usuario ha aprendido.
Ejemplo: ¿Qué es localhost? ¿Qué es un PID? ¿Qué diferencia hay entre ruta absoluta y relativa?

**CAPACIDAD** — Representa lo que realmente puede hacer.
Ejemplo: crear .venv, inspeccionar proceso, calcular hash, localizar módulo, ejecutar dry-run, leer log.

**INTEGRACIÓN** — Representa cuánto del ecosistema puede operar autónomamente.
```
Linux → ECN → WRIL → Protocol → MFN
```

Esto evita una trampa clásica de la gamificación: confundir actividad con aprendizaje.

Y se agrega una cuarta métrica, la más neurobitrónica:

**COMPRENSIÓN** — Porque `EJECUTÉ ≠ ENTENDÍ`.

El sistema puede preguntarle: "¿Qué acaba de modificar este comando?" Si responde correctamente: +comprensión. Si no: ofrecer explicación (sin penalizar). Así aparece una pedagogía potente:

```
hacer → observar → explicar → comprender → repetir
```
